## 问题 1 — 面板圆角仍是方角，且只有左上角是圆的

**现象（Frank 原话）**
> 助手工具栏的面板还是方角，要改成圆角。图标已经是圆角，这很好。哦，仔细看了下，面板是只有左上角加了圆角，其余角还是直角。

**代码定位**
- `crates/pla-ui/src/main.rs:50` — `const ROUNDING: f32 = 6.0;`
- `main.rs:243-248` — `panel_frame()`：`Frame::none().fill(COL_PANEL).rounding(Rounding::same(ROUNDING))`
- `main.rs:71-78` — 主视口 `with_transparent(true)`、`with_decorations(false)`
- `main.rs:405-413` — 子视口 builder 同样 `with_transparent(true)`

**初步判断**
`Rounding::same(6.0)` 是**四角一致**的，代码里没有任何单角处理。所以"只有左上角圆"大概率不是 egui 画错，而是**窗口透明没真正生效**：egui 画了圆角矩形，但底层 OS 窗口是不透明方框，四角露出底色，看起来就是直角。左上角之所以显得圆，可能是描边/抗锯齿在该角落生效，或 DWM 对无边框窗口的处理差异——**这一点需要截图实测确认，不要直接下结论**。

**建议排查顺序**
1. 先临时去掉 `v.window_stroke`（`main.rs:204`）和 `panel_frame()` 的边框，只看纯填充，确认四角是否还方。
2. 验证 `with_transparent(true)` 在 Windows 上是否真的让 clear color 全透明（需要分层窗口 + `WS_EX_LAYERED`，eframe 的 glow 后端在部分 Windows 版本上会退化）。
3. 若透明不可靠，退路是 Win32 `SetWindowRgn` 做圆角裁剪——最稳，代价是边缘有锯齿（可配合 2× 超采样缓解）。
4. 最后才是"渲染时把四角像素刷透明"这种 hack，不推荐优先用。

## 问题 2 — 工具栏位置仍遮住文件名

**现象（Frank 原话）**
> 助手工具栏位置还是不对，把文件名遮住了。如果抓取不到文件名区域，那就从当前位置固定往后一段距离，把文件名让出来，这个暂时应该不是大问题。

**代码定位**
- `main.rs:39` — `const SNAP_LEFT_OFFSET: f32 = 250.0;`
- `main.rs:41` — `const SNAP_TOP_GAP: i32 = 2;`
- `main.rs:34` — `const TOOLBAR_SIZE: [f32; 2] = [264.0, 30.0];`
- `main.rs:381` — `let x_phys = target.left as f32 + SNAP_LEFT_OFFSET;`

**判断**
R4 已把吸附从"右缘 -150"改成"左缘 +250"，但仍压在文件名上。Plasticity 标题栏里文件名靠左排，250 物理像素不够。

**建议（按 Frank 的明确指示）**
- **不要去做文件名区域的窗口控件探测**——Frank 已说明"抓取不到就固定偏移"。
- 直接把 `SNAP_LEFT_OFFSET` 调大到越过文件名（需要 Frank 给一个目测值，或截图标尺量一下），并把该值做成常量注释说明"含文件名避让"。
- 注意单位：当前 `x_phys` 是物理像素，再 `/ ppp` 转 points 发给 `OuterPosition`，这个换算是对的，改常量时不要动换算逻辑。
- 高 DPI 下若偏移量需要随缩放变化，再考虑乘 `ppp`；先按固定物理像素解决当前问题。

## 问题 4 — 刷实体失败（Frank 推测是模型庞大）

**现象（Frank 原话）**
> 刷实体刷失败了，可能因为用的模型比较庞大，可能要换一种方式解析实体树。

**代码定位**
- `crates/pla-ui/src/bridge_thread.rs:127-135` — `RefreshEntities` → `client.list_visible()`，`tokio::time::timeout(5s)` 包裹
- `crates/pla-bridge/src/connection.rs:178-181` — `list_visible()` 发 `MessageType::ListVisible`
- `crates/pla-bridge/src/protocol.rs:37` — `ListVisible = 22`（**码22 全树**）

**关键判断：这不是"解析"的问题，是"取数"的问题**

已知实锤（见 `pitfalls.md` / 项目记忆）：**码22 全树单帧上限 ≈ 368040 B，超出部分静默截断**。

所以机制是：模型越大 → 全树帧越大 → 超过 368KB → 被服务端静默截断 → 收到不完整帧 → 解析失败。**跟"模型庞大连解析都扛不住"无关**，也不需要"换一种方式解析实体树"。换解析算法不会有用，因为数据在传输层就已经丢了。

**建议方向（补分片，不是换解析器）**
1. **先让失败可见**：收到帧时若长度逼近 368040，判定为截断并显式报错（`实体树过大，超出单帧上限，需分片拉取`），而不是静默失败或给个笼统错误。这一步成本最低，且能避免后续误判。
2. **试 `ListSome(21)`**：按父节点/子树分批拉，天然规避单帧上限。
3. **试码22 带参分页**：探针试 offset/limit 类参数，验证是否支持翻页。
4. 分片机制落地前，**不要动实体树解析算法**。

对应 TODO #9「码22 分块查询/翻页机制逆向（或探针试带参请求）」。这条现在是 P0——它直接决定核心功能可用性。
